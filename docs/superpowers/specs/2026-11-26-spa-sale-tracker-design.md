# SPA 브랜드 세일 트래커 — 설계

작성일: 2026-11-26

## 왜 만드는가

무신사 스탠다드, 유니클로, SPAO 같은 SPA 브랜드의 세일 상품을 사이트마다 돌아다니며 찾는 게 번거롭다.
주 용도는 **사고 싶은 특정 상품이 싸졌는지 확인하는 것**이고, 부가 용도로 **지금 세일 중인 상품을 한 화면에서 둘러보는 것**도 원한다.
가격이 내려가면 직접 확인하지 않아도 **이메일로 알림**을 받아 세일을 놓치지 않는 것이 핵심 가치다.

## 목표

1. 관심 상품(상품 링크로 지정)의 현재가·정가·할인율·가격 변동을 보여준다.
2. 관심 상품 가격이 내려가면 이메일로 알린다.
3. 지원 브랜드의 세일 상품 전체를 한 화면에서 할인율순으로 둘러보고, 검색·브랜드·가격으로 거를 수 있다.
4. 둘러보기 화면에서 관심 상품으로 바로 추가할 수 있는 동선을 제공한다.
5. 서버 운영 없이 무료로 돌아간다.

## 비목표

- 조건 기반 검색 알림(예: "검은 니트 5만원 이하") — 사용자가 특정 상품 지정 방식을 선택함.
- 화면에서 즉시 관심 상품 저장(로그인·DB가 필요한 기능).
- 여러 사용자 지원. 개인용이다.
- 구매·장바구니 연동.
- 사이즈·색상별 재고 확인(사용자 결정: 1차는 가격만 본다). 세 브랜드 수집이 안정된 뒤 추가를 검토한다. 그때 `watchlist.txt`에서 URL 뒤에 사이즈를 적을 수 있도록, 줄 형식은 확장할 여지를 남겨 둔다.

## 안티골 (돌아가더라도 실패인 경우)

- 수집이 조용히 멈춰서 알림이 안 오는데 사용자가 모르는 상태.
- 같은 가격 하락에 대해 알림이 반복돼서 메일이 스팸처럼 쌓이는 상태.
- 사이트에 부담을 줄 만큼 자주 또는 많이 요청하는 것.

## 제약

- 대상 사이트에 공개 API가 없다. 사이트 페이지나 사이트가 내부적으로 쓰는 엔드포인트에서 데이터를 가져와야 하고, 사이트 구조가 바뀌면 깨질 수 있다.
- 무신사는 봇 차단이 있을 수 있고, GitHub Actions(클라우드 IP)에서 막힐 가능성이 있다.
- 저장소는 **공개**한다(사용자 결정). 관심 목록과 가격 기록은 누구나 볼 수 있다. 이메일 주소와 비밀번호는 GitHub Secrets에만 둔다.
- 무료로 운영한다. 공개 저장소에서는 GitHub Actions와 GitHub Pages가 무료다.

## 검토한 방식

| 방식 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. GitHub Actions + Pages (선택)** | Actions가 정기적으로 수집해 JSON을 커밋하고, 정적 페이지가 그 JSON을 읽음 | 무료, 서버 없음, 관리 부담 적음 | 화면에서 즉시 등록 불가(GitHub에서 파일 편집) |
| B. 웹 서버 + DB (Vercel/Cloudflare 등) | 화면에서 바로 찜하기 | 등록 동선이 가장 편함 | 무료 요금제 한도(크론 빈도, 실행 시간, DB 휴면)를 관리해야 함 |
| C. 로컬 PC + 작업 스케줄러 | PC에서 실행 | 가장 단순 | PC가 꺼지면 수집과 알림이 멈춤. 알림 목적과 맞지 않음 |

A를 고른 이유: 등록은 가끔 하고, 대부분은 알림과 화면 확인이다. 그래서 단순하고 무료인 쪽이 낫다.
알림은 처음에 텔레그램을 검토했지만, 사용자가 텔레그램을 쓰지 않아서 **이메일(Gmail)**로 결정했다. 그 때문에 텔레그램으로 링크를 공유해 등록하는 기능은 빠졌다.

## 사용자가 결정한 사항

- 관심 상품은 **상품 링크**로 지정한다.
- 알림은 **이메일**로 받는다.
- 방식 **A**를 쓰고, 저장소는 **공개**한다.
- 관심 상품 등록은 **GitHub 웹에서 관심 목록 파일을 편집**하는 방식으로 한다.
- 알림은 **가격만 기준**으로 하고, 재고는 보지 않는다.
- 화면은 관심 상품이 위에, 전체 세일 목록이 아래에 오는 구성이다.

```
[검색: 니트      ] [브랜드 ▾] [할인율 ▾] [가격 ▾]
──────────────────────────────────────────
내 관심 상품:  히트텍 크루넥(유니클로) 14,900원 ↓20% (최저가)  · …
──────────────────────────────────────────
전체 세일 (할인율순)
[img] [img] [img] [img]   ← 각 카드에 "관심 추가" 링크
```

## 설계 (빌더가 판단한 사항은 *[판단]*으로 표시)

### 구성

- **수집기**: Python. 브랜드마다 모듈 하나를 두고, 공통 인터페이스 두 가지를 구현한다.
  - `fetch_sale_items() -> list[Product]`
  - `fetch_product(url) -> Product`

  브랜드를 추가하려면 모듈 하나를 추가하고 등록하면 된다. *[판단]*
- **Product 필드**: 브랜드, 상품 ID, 이름, 상품 URL, 이미지 URL, 정가, 현재가, 할인율, 수집 시각.
- **세일의 정의**: 현재가가 정가보다 낮은 상품. 유니클로의 "기간한정가격"도 포함한다. *[판단]*
- **실행**: GitHub Actions 스케줄로 하루 4회 실행한다. 한국 시간 기준 08·12·18·22시. 수동 실행(workflow_dispatch)도 지원한다. *[판단]*
- **저장**: 저장소 안 `data/` 아래 JSON 파일에 저장하고, 변경이 있을 때만 커밋한다.
  - `data/sale_items.json`: 현재 세일 목록 스냅샷. 이력을 남기지 않고 덮어쓴다.
  - `data/watch.json`: 관심 상품별 가격 이력. 가격이 바뀌었을 때만 기록을 추가한다.
  - `data/status.json`: 브랜드별 마지막 성공 시각, 연속 실패 횟수.

  가격 이력은 관심 상품만 남겨서 저장소가 커지는 것을 막는다. *[판단]*
- **관심 목록 파일**: 저장소 루트의 `watchlist.txt`. 한 줄에 상품 URL 하나를 쓰고, `#`으로 시작하는 줄은 주석이다. URL을 보고 브랜드를 자동으로 판별한다. *[판단]*

### 알림

- **보내는 방법**: Gmail SMTP와 앱 비밀번호를 사용한다. Secrets에 `GMAIL_ADDRESS`, `GMAIL_APP_PASSWORD`, `ALERT_TO`를 둔다.
- **알림 조건**: 관심 상품의 현재가가 직전 기록 가격보다 낮아졌을 때만 보낸다. 같은 가격이 유지되면 다시 보내지 않는다. *[판단]*
- **메일 형식**: 한 번 실행에서 생긴 하락은 메일 한 통으로 묶는다. 상품마다 이전가→현재가, 할인율, 역대 최저가 여부, 상품 링크를 넣는다. *[판단]*
- **수집 실패 알림**: 어떤 브랜드든 3회 연속 수집에 실패하면 경고 메일을 한 번 보낸다. 같은 실패가 이어지는 동안에는 다시 보내지 않고, 복구된 뒤 다시 실패하면 그때 다시 보낸다. "조용히 멈춤" 안티골에 대응하기 위한 장치다. *[판단]*
- **새로 등록한 상품**: 처음 수집한 가격은 기준값으로만 기록하고 알림을 보내지 않는다. *[판단]*

### 화면

- `site/` 폴더의 정적 HTML과 바닐라 JS로 만들고, GitHub Pages로 배포한다. 페이지는 `data/*.json`을 읽는다. 휴대폰 화면을 우선해 반응형으로 만든다. *[판단]*
- **관심 상품 영역**: 현재가, 정가, 할인율, 이력 기반 작은 가격 추이 그래프, 최저가 표시를 보여준다. 등록했지만 수집에 실패한 URL은 오류 표시와 함께 보여준다.
- **둘러보기 영역**: 할인율순으로 기본 정렬하고, 검색어·브랜드·할인율·가격으로 거를 수 있다.
- **관심 추가**: 카드의 "관심 추가"를 누르면 상품 URL을 클립보드에 복사하고, GitHub의 `watchlist.txt` 편집 화면을 새 탭으로 연다. *[판단]*
- **수집 시각**: 브랜드별 마지막 수집 시각을 표시해서, 데이터가 오래됐으면 바로 알 수 있게 한다.

### 사이트 부담 및 예의

- 요청 사이에 지연을 두고, 세일 목록은 페이지 수에 상한을 둔다. 일반적인 브라우저 User-Agent를 쓰되, 개인 정보는 넣지 않는다.

## 위험과 첫 단계

**첫 작업은 브랜드별 수집 가능성 검증이다.** 세 사이트에서 각각 세일 목록과 개별 상품 가격을 어떤 경로(내부 JSON 엔드포인트, HTML 파싱, 헤드리스 브라우저)로 가져올 수 있는지 확인하고, GitHub Actions 환경에서도 실제로 되는지 확인한다.
어떤 브랜드가 Actions에서 막히면 바로 사용자에게 알리고, 해당 브랜드를 어떻게 처리할지 다시 결정한다. 이 상황은 우회하지 않고 사용자와 상의한다.

## 빌더에게 맡기는 것

- 브랜드별 구체적인 수집 경로와 파싱 방법.
- 파일과 모듈 구조의 세부, 테스트 구성. 파서는 저장해 둔 응답 샘플로 테스트하고, 알림 판단 로직은 단위 테스트로 검증한다.
- 화면의 시각 디자인 세부.
